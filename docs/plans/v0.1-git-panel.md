# Plan: v0.1, a fast git panel

- **Title:** v0.1, a fast git panel
- **Date:** 2026-09-26 (rewritten the same day; it started as a read-only diff
  viewer)
- **Description:** A native macOS git panel that sits next to any editor,
  borrowing its core concepts from Zed's git panel. See what changed, read the diff, stage
  files, hunks, or lines, commit, switch branches, and push or pull. Commit
  history stays as a second tab.
- **Problem it solves:** Reviewing and committing your work means leaving the
  editor for a full git client or the terminal, and that's slow enough that
  reviews get skipped and commits get sloppy. Adit makes the loop of look,
  stage, commit feel instant and keyboard-driven.

## What it looks like

Borrows Zed's concepts (Changes and History tabs, stage by checkbox, commit box
at the bottom, undo last commit) but is its own design: a standalone Mac app
with a full-size diff pane, native controls, and keyboard-first navigation.
Where Zed's choice doesn't fit a separate window, Adit does its own thing.

- **Sidebar, two tabs: Changes and History.**
- **Changes:** a toolbar with View Diff and a Stage All menu (Stage All,
  Unstage All, Discard All). Below it, changed files in two groups, Staged and
  Changes, each row showing a status letter and path, with a checkbox that
  stages or unstages it. When nothing changed: "No changes to commit".
- **Branch bar:** `repo / branch`. Clicking the branch opens the branch picker.
  A Fetch button with a menu for Pull and Push.
- **Commit box:** message field and a Commit button (menu: Commit, Amend).
  `⌘↩` commits.
- **Last commit:** its summary under the commit box, with an undo button that
  un-commits and keeps the changes staged.
- **History:** the commit list, newest first. Selecting a commit shows its diff.
- **Detail pane:** the diff of whatever is selected: a working file's unstaged
  or staged changes, or a commit. Unified or split.

## Not in this release

Rebase, merge, conflict resolution, stash, cherry-pick, tags, submodules,
blame, syntax highlighting, and search. Each one makes Adit a bigger client;
none makes the look, stage, commit loop faster. (AI commit messages were listed
here for v0.2; they shipped early.)

## Speed budgets

Hard limits, not goals. A step that misses one is not done.

- **Launch to first list:** under 300 ms from cold start, on any repository.
- **Select a file or commit to diff painted:** under 50 ms for a typical diff
  (under 1,000 changed lines).
- **Large diffs:** first screen painted in under 100 ms for 10,000+ lines, such
  as a lockfile.
- **Working tree status:** under 50 ms for a repository with 10,000 tracked
  files.
- **Edit a file on disk to the Changes list updating:** under 200 ms,
  debounce included.
- **Stage, unstage, commit:** the list reflects it in the next frame; the index
  or commit is written within 100 ms.
- **Navigation:** `j`/`k`, file jumps, and hunk jumps respond within one frame
  (16 ms at 60 Hz).
- **Main thread:** never waits on libgit2. Git work runs on the actor, and views
  only receive finished value types.

Measured with the benchmark mode (`-AditBenchmark YES`, see `App/Benchmark.swift`)
on a Release build. Every step from here on is timed as it lands.

## Measured

Release build, benchmark mode, 2026-09-26, after the speed work. "Adit" is this
repository (recent commits of a few hundred lines); "10k" is a generated
repository with 10,000 tracked files and a 200,000-line first commit. Frame
work is timed with layout, display, and the Core Animation commit forced
synchronously, so vsync waits aren't counted.

| | Adit | 10k | Budget |
|---|---|---|---|
| Launch to first list (warm) | 204 to 356 ms | 234 to 350 ms | 300 ms |
| Full status | 7 to 13 ms | ~60 ms | 50 ms |
| Status after an edit (changed files only) | | a few ms | 16 ms |
| Switch commit, to diff painted | ~45 ms avg | ~35 ms | 50 ms |
| 200k-line diff, first screen | | ~90 ms | 100 ms |
| Stage, unstage, partial staging | 10 to 56 ms | | 100 ms |
| Commit (system git) | 54 ms | | 100 ms |
| Hunk jump | ~15 ms | 0.6 ms | 16 ms |
| File jump | ~21 ms | 0.1 ms | 16 ms |
| Collapse, expand | 16 to 24 ms | 11 to 13 ms | 16 ms |
| Layout toggle | 47 to 49 ms | 34 to 42 ms | 16 ms |

What changed: row views reused and drawn into one layer each; a spurious
full rebuild on every jump removed; line widths counted once off the main
thread so row heights are arithmetic; rows for huge diffs built in the
background; huge diffs paint their first screen first and open with later
files collapsed; collapse swaps only that file's rows; status after an edit
checks only the files that changed.

**Still over budget:**

1. **Layout toggle** rebuilds and reloads every row (~35 to 50 ms). Rare, and
   no single hotspot left; next would be keeping both layouts' rows built.
2. **File jumps** that land on unseen rows (~21 ms) pay for laying out a
   screenful of new ones.
3. **Full status on 10k files** (~60 ms) is the cost of checking every file;
   it now runs only on open, on activation, and after index or HEAD changes.
4. **Launch** goes over 300 ms on the first launch after a new build, when
   macOS checks the new binary; warm launches are within budget.

Diff algorithm: libgit2 exposes Myers (the default) and patience, not
histogram, though its bundled xdiff implements histogram. Nugroho et al.
(EMSE 2020) found histogram gave the better diff for 62.6% of changed code
files against 16.9% for Myers. Using it needs a small local patch to libgit2's
diff flags; record it in `VENDORED.md` if made.

## Steps

1. **Status.** `git_status_list` into a `FileStatus` model: staged, unstaged,
   untracked, conflicted, with rename detection off. Time it against the
   status budget on a large repository before building any UI on it.
2. **Changes tab.** Sidebar tabs, the Changes list with Staged and Changes
   groups, the empty state. History moves to its own tab unchanged.
3. **Working-tree diffs.** Index to working tree for unstaged, HEAD to index for
   staged, untracked files as all additions. Same renderer as commits.
4. **Live refresh.** Watch the repository with FSEvents, debounced, and
   refresh status when files, the index, or HEAD change. Also refresh when the
   app comes forward.
5. **Stage and unstage files.** Checkbox, Space on the selected row, Stage All,
   Unstage All. The list updates optimistically; the index write follows.
   Handle `index.lock` held by another git process with a clear message, not a
   crash.
6. **Discard.** Discard a file's unstaged changes, or all of them. Always asks
   first: this is the one action that can lose work.
7. **Commit.** Message field, `⌘↩`, Amend, undo last commit (soft reset).
   Commits run system git, so hooks, signing, and config apply.
8. **Hunk and line staging.** Stage or unstage one hunk from its header, or
   selected lines, by building a patch and applying it to the index
   (`git_apply` with `GIT_APPLY_LOCATION_INDEX`). Heavily tested: a wrong patch
   here corrupts what gets committed.
9. **Branches.** Branch picker in the branch bar: switch and create, through
   system git, which refuses when local changes would be overwritten.
10. **Push, pull, fetch.** System git, with ahead and behind counts in the
    branch bar.
11. **Measure.** Every budget above, on Adit's repo and on a large one. Done;
    results and what's still over are under Measured.

## Next: folders with several repositories

Some projects are a plain folder holding several repositories side by side.
`~/projects/python/papercheck` is the case this is designed against: it isn't
a repository itself, and holds three (`ai-thesis-coach`, 1,219 tracked files;
`ai-thesis-coach-fastapi`, 1,081; `documents`, 33) next to shared `docs/`,
`AGENTS.md`, and `CLAUDE.md`. Work often touches the frontend and backend at
once, and today Adit can only open one of them, and says the parent "isn't
inside a git repository".

12. **Find the repositories.** Opening a folder that isn't inside a repository
    scans it for repositories instead of failing: children up to three levels
    down with a `.git` folder or a `.git` file (linked worktrees and
    submodule-style checkouts use a file; `ai-thesis-coach` has a linked
    worktree). Skip `node_modules`, `.build`, `DerivedData`, `Pods`, `.venv`,
    and other dependency folders, and don't descend into a repository once
    found. No repositories: say so, as today. Budget: under 50 ms for a folder
    like papercheck.
13. **A workspace, with one repository active.** The session holds a list of
    repositories and one active `GitRepository`; the rest open lazily. The
    bookmark remembers the folder and which repository was active. The file
    watcher watches the folder once and routes each event to the repository
    whose path contains it.
14. **Repository picker.** Borrowed from Zed: the repository name in the branch
    bar (`repo / branch`) becomes a picker, like the branch name. Each entry
    shows its branch and how many changes it has, so you can see at a glance
    which repositories need attention. `⌘⇧R` opens it; `⌘1` to `⌘9` jump to a
    repository directly. Changes, History, the commit box, the branch picker,
    and sync all act on the active repository.
15. **Changes across all of them.** Status runs for every repository in the
    background (the active one first) to keep the picker's counts current.
    An "All repositories" entry in the picker shows every repository's changes
    in one list, grouped under a header per repository, for the frontend and
    backend edited together case. Committing still happens one repository at a
    time: in that view, the commit box names the repository it will commit to,
    and switching groups switches the active repository.
16. **Rules from the parent folder.** For AI messages, look for `AGENTS.md` or
    `CLAUDE.md` in the repository first, then in the workspace folder, since
    papercheck keeps them at the top.

Budgets: switching the active repository to its diff painted under 100 ms after
first open; status for all three papercheck repositories, in the background,
under 150 ms together. Neither blocks the main thread.

## Next: changes the research supports

From a review of the research on reading diffs and writing commit messages
(2026-09-26). Each step names its evidence; claims without evidence (side by
side beats unified, syntax-aware diffs help reviewers, syntax highlighting aids
comprehension) are deliberately not acted on.

17. **File order that isn't alphabetical.** Files shown later in a review get
    fewer comments, and one kind of defect had 64% lower odds of being found in
    the last file than the first (Fregnan et al., ESEC/FSE 2022). Only 10.2% of
    1,355 developers call alphabetical order best, and 66% want to set it
    themselves (Rahman et al., ICSE 2026). Default order: source files first,
    each followed by its tests; then configuration; then lockfiles, generated,
    and vendored files last (they're long and rarely read line by line).
    Within those groups, keep folders together. A per-repository toggle back to
    path order for anyone who prefers it. Applies to the Changes list, View
    All, and commit diffs. Budget: sorting adds under 1 ms for 1,000 files.
18. **Histogram diffs.** Histogram produced the better diff for 62.6% of
    changed code files against 16.9% for Myers, and the two tied on most other
    files (Nugroho et al., EMSE 2020). libgit2 doesn't expose it, but its
    bundled xdiff implements it: add a `GIT_DIFF_HISTOGRAM` flag that maps to
    xdiff's histogram mode, record the patch in `VENDORED.md`, and use it for
    every diff Adit makes, including the ones hunk staging patches are built
    from. Check that it stays inside the diff budgets on the 171k-line commit;
    fall back to Myers above a size limit if it doesn't.
19. **Change size up front.** Small, single-purpose changes review better
    (Sadowski et al., ICSE-SEIP 2018; Baum et al., EMSE 2019), and splitting
    mixed changes makes them easier to understand (Tao & Kim, MSR 2015). Show
    the staged change's size in the commit box (files, lines added and
    removed) so a large commit is visible before it's made. No warnings or
    thresholds: the evidence supports small changes, not any particular line
    count (the common 200 to 400 line rule traces to a vendor case study).
20. **Commit messages that say why.** About 44% of real commit messages fall
    short, and the reason for a change is missing twice as often as what
    changed (Tian et al., ICSE 2022). Recent commit history makes generated
    messages better (Eliseeva et al., ASE 2023), and generators produce either
    very good or very bad messages, so weak ones are better held back (Jiang
    et al., ASE 2017).
    - Send the last 10 commit subjects with the diff, so messages match the
      repository's style.
    - Ask the model for a body only when the diff shows why; otherwise have it
      stop at the subject rather than guess.
    - If you've typed anything beyond a subject, treat it as the why and have
      the model keep it.
    - Hold back replies that match Tian et al.'s weak patterns (a single word,
      only a scope such as "minor changes", or just restating a file name):
      show "That one wasn't useful, try again or pick another model" instead
      of filling the box.
    - Measure quality the way JetBrains found tracks real use: how much you
      edit a generated message before committing (Tsvetkov et al., ICSE 2025).
      Log the edit distance locally with the other timings; never send it.

## Next: a terminal

A terminal right beside the diff, for the commands around a commit: run the
tests, check `git log -p`, fix a hook failure. It earns its place by keeping
you in Adit through a commit, not by replacing your terminal app.

21. **Open in Terminal.** One key (⌘T) opens your terminal app (Ghostty,
    Terminal, iTerm, or Warp; picked in Settings) at the active repository.
    Cheap, and uses the terminal you already have set up.
22. **Built-in terminal panel.** A panel under the diff, toggled with ⌃`,
    started in the active repository and following it when you switch
    repositories. Runs your login shell with your PATH, like git commands
    already do. Keys typed there never reach Adit's single-key commands. Needs
    a terminal emulator library; SwiftTerm (MIT licence, used by several Mac
    apps) is the likely choice, to be recorded in the decision log. Budget: the
    panel opens in under 100 ms, and a shell that's already running is kept
    when you hide and show it.

Open question: whether 22 is worth it after living with 21 for a while. A
built-in terminal is the kind of feature that grows; the scope rule in the
decision log applies to it.

## Next: from using it

26. **Branch diff.** See everything a branch changes without checking
    anything out, like Zed's "View Branch Diff". A "Branch" entry at the top of
    History diffs the branch against where it split from its base (main, or
    the upstream's default branch), plus any uncommitted work, in the same diff
    view. Works for watching a feature branch grow as commits land.
27. **Configurable keyboard shortcuts.** A Shortcuts tab in Settings listing
    every command with its key, where you can record a new key or clear one.
    Conflicts are flagged before they're saved; single-letter keys stay
    limited to commands that never fire while typing. Stored in UserDefaults,
    with a reset to defaults.

## Decided: system git for network and commits

Push, pull, and fetch need the user's credentials, which a sandboxed app can't
reach. The sandbox is off, and commit, branch switching, fetch, pull, and push
run system git, so they behave exactly like the terminal, hooks and signing
included. See the decision log.

## Risks

- **Hooks need the user's PATH.** Apps launched from the Dock get a minimal
  PATH, so hooks that call `npx` or `bundle` fail. Resolve PATH from the login
  shell once and hand it to every git process.
- **Concurrent git.** The editor, the terminal, and Adit all write the index.
  Re-read before every write, and treat a held `index.lock` as "try again", not
  an error to report.
- **Partial staging correctness.** Step 8 is the easiest place to commit the
  wrong thing. Test against `git apply --cached` output on real diffs.
- **Discard loses work.** Confirmation every time, and no keyboard shortcut
  that can trigger it by accident.
- **Large repositories.** Status and FSEvents on a monorepo can blow the
  budget. Measure early (step 1), not at the end.
