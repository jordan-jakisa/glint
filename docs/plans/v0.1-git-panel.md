# Plan: v0.1, a fast git panel

- **Title:** v0.1, a fast git panel
- **Date:** 2026-09-26 (rewritten the same day; it started as a read-only diff
  viewer)
- **Description:** A native macOS git panel that sits next to any editor,
  borrowing its core concepts from Zed's git panel. See what changed, read the diff, stage
  files, hunks, or lines, commit, switch branches, and push or pull. Commit
  history stays as a second tab.
- **Problem it solves:** Reviewing and committing your work means leaving the
  editor for a full git client or the terminal, and that's slow enough that
  reviews get skipped and commits get sloppy. Adit makes the loop of look,
  stage, commit feel instant and keyboard-driven.

## What it looks like

Borrows Zed's concepts (Changes and History tabs, stage by checkbox, commit box
at the bottom, undo last commit) but is its own design: a standalone Mac app
with a full-size diff pane, native controls, and keyboard-first navigation.
Where Zed's choice doesn't fit a separate window, Adit does its own thing.

- **Sidebar, two tabs: Changes and History.**
- **Changes:** a toolbar with View Diff and a Stage All menu (Stage All,
  Unstage All, Discard All). Below it, changed files in two groups, Staged and
  Changes, each row showing a status letter and path, with a checkbox that
  stages or unstages it. When nothing changed: "No changes to commit".
- **Branch bar:** `repo / branch`. Clicking the branch opens the branch picker.
  A Fetch button with a menu for Pull and Push.
- **Commit box:** message field and a Commit button (menu: Commit, Amend).
  `⌘↩` commits.
- **Last commit:** its summary under the commit box, with an undo button that
  un-commits and keeps the changes staged.
- **History:** the commit list, newest first. Selecting a commit shows its diff.
- **Detail pane:** the diff of whatever is selected: a working file's unstaged
  or staged changes, or a commit. Unified or split.

## Not in this release

Rebase, merge, conflict resolution, stash, cherry-pick, tags, submodules,
blame, syntax highlighting, search, and AI commit messages (v0.2). Each one
makes Adit a bigger client; none makes the look, stage, commit loop faster.

## Speed budgets

Hard limits, not goals. A step that misses one is not done.

- **Launch to first list:** under 300 ms from cold start, on any repository.
- **Select a file or commit to diff painted:** under 50 ms for a typical diff
  (under 1,000 changed lines).
- **Large diffs:** first screen painted in under 100 ms for 10,000+ lines, such
  as a lockfile.
- **Working tree status:** under 50 ms for a repository with 10,000 tracked
  files.
- **Edit a file on disk to the Changes list updating:** under 200 ms,
  debounce included.
- **Stage, unstage, commit:** the list reflects it in the next frame; the index
  or commit is written within 100 ms.
- **Navigation:** `j`/`k`, file jumps, and hunk jumps respond within one frame
  (16 ms at 60 Hz).
- **Main thread:** never waits on libgit2. Git work runs on the actor, and views
  only receive finished value types.

Measured with the benchmark mode (`-AditBenchmark YES`, see `App/Benchmark.swift`)
on a Release build. Every step from here on is timed as it lands.

## Done

From the first version of this plan, all on branch `v0.1-diff-viewer`:

1. libgit2 vendored from source (`Packages/Clibgit2`), confined to the
   `GitRepository` actor.
2. Repo picker with a security-scoped bookmark; the last repository reopens on
   launch.
3. Commit history, paged, newest first.
4. `FileChange`, `Hunk`, `DiffLine` models built at the git boundary.
5. Unified and split diffs with line numbers and per-file collapse, drawn by an
   `NSTableView` (the SwiftUI version missed the budget by 2x).
6. Keyboard: `j`/`k` commits, `⌘↓`/`⌘↑` files, `n`/`p` hunks, `o` collapse,
   `⌘\` layout.
7. Timing logs and the benchmark mode.

Last measured (Release, Adit's own repo): launch 245 to 356 ms, commit switch
15 to 56 ms, a 171k-line commit 69 to 105 ms. **Still over budget:** hunk and
file jumps at about 38 ms and layout toggle or collapse at about 45 ms. Rows
are laid out as text on every draw; caching the laid-out lines per row is the
first thing to try.

## Steps

1. **Status.** `git_status_list` into a `FileStatus` model: staged, unstaged,
   untracked, conflicted, with rename detection off. Time it against the
   status budget on a large repository before building any UI on it.
2. **Changes tab.** Sidebar tabs, the Changes list with Staged and Changes
   groups, the empty state. History moves to its own tab unchanged.
3. **Working-tree diffs.** Index to working tree for unstaged, HEAD to index for
   staged, untracked files as all additions. Same renderer as commits.
4. **Live refresh.** Watch the repository with FSEvents, debounced, and
   refresh status when files, the index, or HEAD change. Also refresh when the
   app comes forward.
5. **Stage and unstage files.** Checkbox, Space on the selected row, Stage All,
   Unstage All. The list updates optimistically; the index write follows.
   Handle `index.lock` held by another git process with a clear message, not a
   crash.
6. **Discard.** Discard a file's unstaged changes, or all of them. Always asks
   first: this is the one action that can lose work.
7. **Commit.** Message field, `⌘↩`, Amend, undo last commit (soft reset).
   Commits run system git, so hooks, signing, and config apply.
8. **Hunk and line staging.** Stage or unstage one hunk from its header, or
   selected lines, by building a patch and applying it to the index
   (`git_apply` with `GIT_APPLY_LOCATION_INDEX`). Heavily tested: a wrong patch
   here corrupts what gets committed.
9. **Branches.** Branch picker in the branch bar: switch and create, through
   system git, which refuses when local changes would be overwritten.
10. **Push, pull, fetch.** System git, with ahead and behind counts in the
    branch bar.
11. **Measure.** Every budget above, on Adit's repo and on a large one.

## Decided: system git for network and commits

Push, pull, and fetch need the user's credentials, which a sandboxed app can't
reach. The sandbox is off, and commit, branch switching, fetch, pull, and push
run system git, so they behave exactly like the terminal, hooks and signing
included. See the decision log.

## Definition of done

Jordan uses Adit instead of Zed's git panel or the terminal for a week to
review, stage, and commit his own work.

## Risks

- **Hooks need the user's PATH.** Apps launched from the Dock get a minimal
  PATH, so hooks that call `npx` or `bundle` fail. Resolve PATH from the login
  shell once and hand it to every git process.
- **Concurrent git.** The editor, the terminal, and Adit all write the index.
  Re-read before every write, and treat a held `index.lock` as "try again", not
  an error to report.
- **Partial staging correctness.** Step 8 is the easiest place to commit the
  wrong thing. Test against `git apply --cached` output on real diffs.
- **Discard loses work.** Confirmation every time, and no keyboard shortcut
  that can trigger it by accident.
- **Large repositories.** Status and FSEvents on a monorepo can blow the
  budget. Measure early (step 1), not at the end.
